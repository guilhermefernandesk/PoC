Módulo 00 — Por que firmware é diferente (e por que isso muda o uso da IA)

Tempo: 25 min · Entrega: mental model das 6 camadas + claude funcionando no seu projeto.

1. O problema que este workshop resolve

Quase todo tutorial de IA para código follow along com uma API REST: roda teste em 2 segundos, vê erro, corrige, pronto. Firmware não é assim:

Característica Consequência para o agente
RAM/Flash contadas em bytes "Funciona no meu host" não significa nada. O agente precisa saber o orçamento.
Hardware fora do processo Compilar não prova que o pino 5 do GPIO está certo. Falta o loop HIL.
Erra de silício / errata O modelo não vê o datasheet revisão C. Tem que entrar no contexto.
Feedback lento (flash, reset, serial) Cada iteração custa tempo e desgaste da bancada. Retrabalho é caro.
Concorrência e ISR Bug depende de timing; teste determinístico precisa de mock e disciplina.
Release é binário com versão Rastrear v1.4.2 até o requisito é parte do produto, não burocracia.

Frase para guardar: a IA não é o problema; o problema é ela decidir com informação incompleta e ninguém ter um cheque determinístico para barrar.

2. O mapa de 6 camadas

Todo o resto do workshop é uma das camadas abaixo:

1. CONTEXTO      CLAUDE.md, SPEC.md, @arquivo, regras por caminho
2. SKILLS        procedimentos carregados só quando chamados
3. ISOLAMENTO    subagents, worktrees, permissões, sandbox
4. HOOKS         regras que o harness executa (não o modelo)
5. INTEGRAÇÃO    MCP/CLI, GitLab Issues e MRs, plugins
6. ORQUESTRAÇÃO  GitLab CI, scheduled tasks, Agent SDK (opcional)

Camadas 1–2 aumentam acertividade. Camadas 3–4 aumentam segurança e previsibilidade. Camadas 5–6 fecham o ciclo de evidência.

3. Superfícies: uma config, vários lugares

Claude Code roda em terminal, VS Code, JetBrains, Desktop e Web. O motor é o mesmo: CLAUDE.md, .claude/settings.json, skills e MCP valem em todos. Não estude "Claude Code da IDE" separado do da CLI.

curl -fsSL https://claude.ai/install.sh | bash

# primeiro contato

> /quickstart

4. Exercício 00 — explorar sem editar

No diretório do seu projeto GitLab (ou no capstone/ deste material):

Você é um novo dev no projeto. Sem modificar nenhum arquivo:
1. descubra como o firmware é compilado e gravado;
2. aponte onde ficam as regras de negócio versus os drivers;
3. diga qual comando você usaria para rodar só os testes unitários;
4. liste três coisas que você NÃO consegue saber lendo o código.

Por que "sem modificar"? Porque o objetivo do primeiro contato é medir o que o agente consegue inferir. A diferença entre o que ele inferiu e o que você sabia é exatamente o conteúdo do CLAUDE.md que você vai escrever no Módulo 01.

Saia com Esc. Se quiser desfazer algo: /rewind.

5. Erros comuns de quem vem de GitHub Copilot

  • Prompt vago: "melhore esse firmware". Sem alvo de verificação, o agente escolhe o próprio critério de pronto.
  • Pedir para "testar no hardware" sem dizer qual hardware. Ele não tem ST-Link; ele tem permissão para chamar st-flash se você deixar.
  • Colar o datasheet inteiro no prompt. Contexto é recurso finito: use @arquivo e trechos, não o PDF completo.
  • Confiar que "a IDE avisou". O agente na CLI não vê o mesmo estado do editor a menos que você dê o erro.
  • Achar que permissão é segurança. Auto mode usa um classificador; regra dura é hook/deny. Ver Módulo 03.

Próximo: Módulo 01 — Contexto que não cabe no código.

Módulo 01 — Contexto que não cabe no código

Tempo: 30 min · Entrega: um CLAUDE.md curto e verificável.

1. A regra de ouro

Escreva no CLAUDE.md somente o que o modelo não consegue descobrir lendo o repo.

Se o arquivo repete o que já está no CMakeLists.txt, ele só custa tokens e atenção em toda requisição. A documentação oficial recomenda menos de 200 linhas e sugere /init como ponto de partida — o trabalho é quase sempre remover linhas.

2. Estrutura que funciona para firmware

# Commands
- Build:      cmake --build build -j
- Unit tests: ceedling test:all
- One test:   ceedling test:test_blink
- Flash:      st-flash --reset write build/firmware.bin 0x8000000

# Conventions
- Regras de negócio ficam em app/; nunca em Drivers/
- HAL gerada pelo CubeMX é somente leitura: nunca editar Drivers/STM32F1xx_HAL_Driver/
- Sem malloc/printf em código de produção; use osal_log()

# Gotchas
- Rev C do ADC exige 1µs extra após CS (ERRATA-042), ver docs/errata.md
- O timer de 32-bit vira em 49,7 dias; sempre compare com Δ, nunca com absoluto
- O job de I2C na bancada não pode rodar em paralelo (ver .gitlab-ci.yml)

# Verification
- Antes de dizer "pronto": ceedling test:all && ./scripts/shellcheck.sh

Quatro seções, ~20 linhas. É o suficiente para mudar o comportamento do agente.

Compare com o que a Beningo usa no artigo sobre Claude Code para firmware: orçamento de RAM/Flash, imagem STM32L476RG, escolha RTOS vs bare-metal, proibição de malloc/printf, referência à errata do I2C. Tudo aquilo é informação ausente do código.

3. Alimente o contexto no prompt, não só no arquivo

O que você tem Como passar
Um arquivo específico @path/para/arquivo.c (cole o conteúdo efetivo na conversa)
Uma captura de tela do oscilloscope / erro do CubeIDE cole a imagem
Saída de comando longa `cat build.log \ claude -p "explique a primeira falha real"`
Uma decisão tomada em reunião escreva em docs/decisions/NNN-titulo.md e referencie no prompt

Prompt específico economiza rodadas. "o ADC lê 0xFF no canal 2, mas o canal 1 está OK; aqui está o analisador lógico" é melhor que "o ADC está ruim".

4. SPEC.md antes de implementar

O fluxo que mais reduz retrabalho:

sessão A (brainstorm)  →  SPEC.md escrita
        ↓
sessão B (limpa)       →  implementação a partir da spec
        ↓
sessão C (revisor)     →  subagent compara diff contra SPEC.md

A doc de best practices recomenda explicitamente: depois que a spec existe, abra uma sessão nova para construir. O sessão A já está contaminada pelas tentativas de interpretação; a B começa com a definição de pronto por escrito.

Exemplo mínimo de SPEC.md:

# REQ-001 — Piscar LED de status

Critérios de aceite:
- [ ] LED alterna a cada 500 ms ± 10% com o sistema em IDLE
- [ ] LED fica aceso contínuo em ERROR
- [ ] A lógica de temporização não usa busy-wait
- [ ] Existe teste unitário para a transição IDLE→ERROR

Fora de escopo: PWM, MQTT, modos de baixo consumo.

5. Regras por caminho: .claude/rules/

Quando a regra só vale em parte do repo, não polua o CLAUDE.md:

<!-- .claude/rules/generated.md -->
---
paths:
  - "Drivers/**"
  - "Middlewares/**"
---

Código gerado pelo CubeMX. Nunca editar diretamente.
Se precisar de uma mudança, altere o .ioc e regenere.

O front matter paths: faz o arquivo ser carregado só quando Claude trabalha naquele trecho. É o mesmo mecanismo de progressive disclosure das skills, aplicado a regras.

6. Preferências pessoais não vão para o repo

# suas preferências, ignoradas pelo Git
echo 'CLAUDE.local.md' >> .gitignore

Use CLAUDE.local.md para coisas como "prefira respostas curtas" ou "sempre mostre o comando antes de rodar". O que é do time fica no CLAUDE.md; o que é seu fica no .local.

Próximo: Módulo 02 — Skills.

Módulo 02 — Skills: procedimentos que carregam só quando precisam

Tempo: 35 min · Entrega: skill /embedded-unit-tests funcional no capstone/.

1. O que uma skill é (e o que não é)

Uma skill é um pacote de instruções com nome e descrição. Claude vê nome + descrição em toda sessão; o conteúdo completo só entra em contexto quando a tarefa combina com a descrição (ou quando você chama /nome).

.claude/skills/
└── embedded-unit-tests/
    ├── SKILL.md              # obrigatório: nome, descrição, passos
    └── references/
        ├── mocking.md        # carregado só se necessário
        └── edge-cases.md     # carregado só se necessário

Isso é progressive disclosure: o custo em contexto é quase zero até a skill ser usada. Por isso procedimento longo (release, auditoria, escrita de ADR) vai para skill, não para CLAUDE.md.

Mecanismo Quando carrega Garante? Melhor uso
prompt só naquele turno não pedido pontual
CLAUDE.md toda sessão não restrições curtas e universais
.claude/rules/*.md quando o caminho bate não regra de uma pasta
skill quando a descrição bate / /chamada não procedimento com etapas
hook / deny rule sempre, pelo harness sim "nunca" e "sempre"

Skill ainda é instrução para o modelo. É ótima para consistência, não para imposição. Imposição é Módulo 03.

2. SKILL.md mínima

---
name: embedded-unit-tests
description: Escreve testes unitários em C para código STM32 com Unity/CMock.
  Use quando o usuário pedir teste, TDD, cobertura ou região crítica de firmware.
---

# Embedded unit tests

1. Descubra o alvo: qual `.c`, qual função, qual efeito observável.
2. Escreva PRIMEIRO o teste em `test/test_<modulo>.c`.
3. Mock de hardware: use CMock para HAL; nunca chame `HAL_GPIO_*` no teste.
4. Cubra os casos de borda em `references/edge-cases.md`.
5. Rode `ceedling test:all`. Se falhar, corrija o código — nunca enfraqueça o teste.
6. Ao final, reporte: arquivo do teste, comando rodado, resultado.

## Regras
- Teste roda no host, sem placa.
- Se o teste exigir hardware, pare e pergunte.

Nome e descrição são o que o agente usa para escolher. Descrição ruim ("ajuda com testes") faz a skill nunca ser chamada. Descrição boa lista gatilhos.

3. As três skills que você deve construir primeiro

Baseado no guia prático da Beningo para desenvolvedores embarcados:

3.1 /user-stories

  • Entrada: requisito em linguagem natural.
  • Saída: história no formato INVEST + critérios Given-When-Then.
  • Por que importa: se o agente não consegue transformar o requisito em critério testável, o requisito está ambíguo — e é melhor descobrir antes do que depois do flash.
  • Require que todo critério tenha um REQ-### rastreável.

3.2 /embedded-unit-tests

  • references/mocking.md: como isolar HAL, ADC, UART, timers.
  • references/edge-cases.md: lista viva com rollover de timer de 32 bits (49,7 dias @1 kHz), wraparound de buffer circular, reentrância de ISR, underrun de DMA, perda de IRQ, valores 0/NULL/UINT32_MAX.
  • Por que importa: o modelo esquece esses casos; a skill não.

3.3 /adr (Architecture Decision Record)

  • Template com contexto, decisão, alternativas, consequências.
  • Seção obrigatória Compliance: "como essa decisão será verificada automaticamente?"
  • Por que importa: fecha o loop entre arquitetura e CI. Decisão sem verificação vira opinião.

4. Chamando e inspecionando

> /skills                      # lista skills disponíveis
> /embedded-unit-tests test_blink.c
> Use a skill /adr para registrar a decisão de usar OSAL

Claude pode iniciar a skill sozinho se a descrição casar com o pedido. Você também pode forçar pelo nome.

5. Exercício 02 — criar a skill de testes

No capstone/:

mkdir -p .claude/skills/embedded-unit-tests/references
  1. Copie o SKILL.md acima.
  2. Crie references/edge-cases.md com 6 casos de borda do seu periférico favorito (timer, I2C, ADC).
  3. Crie references/mocking.md com o comando de mock do CMock para HAL_GPIO_WritePin.
  4. Teste:
> Use a skill embedded-unit-tests para criar o teste da função blink_toggle()
  1. Confira com /context: o conteúdo de edge-cases.md não deve aparecer até a skill ser usada.

6. Erros comuns

  • Skill com 500 linhas e tudo dentro do SKILL.md. Divide em references/. Carregar tudo de uma vez destrói a vantagem.
  • Descrição vaga. Use verbos e gatilhos: "use quando o usuário pedir teste, TDD, cobertura...".
  • Skill usada para impor regra de segurança. Não funciona toda vez. Vai para hook.
  • Skill duplicando CLAUDE.md. A skill ensina *como fazer*; o CLAUDE.md diz *o que é verdade no projeto*.

7. Checklist

  • □ SKILL.md com name e description no front matter.
  • □ Procedimento longo dividido em references/.
  • □ Pelo menos 3 skills: user stories, testes, ADR.
  • □ A skill de ADR tem seção Compliance.
  • □ Testei chamando a skill explicitamente e deixei o Claude escolher sozinho.

Módulo 03 — Menos tokens, mais acerto, menos risco

Tempo: 40 min · Entrega: /usage antes/depois, hook de filtro, Stop hook e sandbox strict.

Este é o módulo mais importante do workshop. Economia, acurácia e segurança são o mesmo mecanismo visto de três ângulos: contexto limpo → menos tokens e menos distração → mais acerto; regra determinística → menos erro e menos risco.

1. Determinístico vs não determinístico

Tipo Onde mora Quem executa Garante?
Não determinístico prompt, CLAUDE.md, skill o modelo decide não
Determinístico hook, deny rule, managed setting o harness executa sim

A documentação oficial dá o diagnóstico melhor possível:

"Se você continuar reforçando uma linha do CLAUDE.md e Claude ainda a ignora, essa linha pertence a um hook. O inverso também vale: se você tem hooks para preferências, apague-os."

Exemplo prático em firmware:

  • "Nunca edite Drivers/ gerado pelo CubeMX" → PreToolUse bloqueando o caminho.
  • "Sempre rode ceedling test:all antes de terminar" → Stop hook com exit 2.
  • "Prefira nomes descritivos" → fica no prompt, sem hook.

2. Menos tokens

2.1 Meça antes de otimizar

/usage

O que olhar:

  • Session → Usage by model: input, output, cache read/write e custo estimado por modelo.
  • Prompt cache (main): 14 requests · 91% of input tokens from cache · 2 misses ... warm (1h TTL). Se o hit rate está baixo, algo está invalidando o cache.
  • Atribuição: porcentagem por skill, subagent, plugin, MCP server e /loop. Um MCP que consome 30% aparece aqui.
  • Recomendações: linhas com share ≥10%, por exemplo 25% Trim ~/code/fw/CLAUDE.md · 49k tokens per request.
  • Tecla f: aplica as correções automáticas que o Claude consegue fazer (v2.1.305+).

O número ao lado do spinner mede só o output do turno (texto + tool calls + thinking), não o input. Não confunda com o total da sessão.

2.2 As seis ações de maior impacto

Ação Comando Por quê
Limpar entre tarefas /rename → /clear → /resume depois /clear custa zero. Uma sessão com 4 tarefas reenvia as 4 em toda pergunta da 5ª.
Compactar com foco /compact keep the firmware changes and the test commands /compact é uma requisição grande; sem foco ele resume demais e você repete contexto.
Descobrir o que ocupa /context, /context all Mostra o consumo real e confirma se o CLAUDE.md foi carregado.
Usar CLI em vez de MCP glab, git, make, st-flash Definições de tools MCP entram no contexto; CLI não adiciona lista de ferramentas.
Modelo certo /model sonnet, model: haiku no subagent Sonnet para rotina; Opus para arquitetura; Haiku para subagent simples.
Esforço certo `/effort low high xhigh max` Thinking é cobrado como output.

Guia de esforço:

  • low — brainstorm, rascunho, rename em poucos arquivos, você revisa cada passo.
  • high / xhigh — bug que você não escreveu, teste flaky, mudança de schema com muitos leitores.
  • max — problema difícil sem supervisão, ex.: caça a vulnerabilidade. Em tarefa comum ele "pensa demais" e cobra mais pelo mesmo resultado.
  • ultrathink — quando só a próxima mensagem precisa de profundidade.
  • MAX_THINKING_TOKENS=8000 — para modelos com budget fixo; modelos adaptativos ignoram e usam /effort.

2.3 Cache: o que derruba o hit rate

Claude Code reprocessa o histórico a cada turno; o cache faz isso a preço de leitura cacheada. Em assinatura o TTL é ~1h; na API ~5min (confirme em /usage).

Cuidado com:

  • pausa longa → cache frio;
  • troca de modelo (/model) → turno não cacheado;
  • /compact e limpeza de tool results → rebuild esperado;
  • mudança em definições de tools (MCP ligado/desligado).

2.4 Hook de pré-processamento: menos log, mais sinal

Em vez de deixar o Claude ler 10.000 linhas de build, filtre antes:

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "command": "~/.claude/hooks/filter-test-output.sh" }
        ]
      }
    ]
  }
}
#!/usr/bin/env bash
# ~/.claude/hooks/filter-test-output.sh
input=$(cat)
cmd=$(printf '%s' "$input" | jq -r '.tool_input.command // ""')

case "$cmd" in
  *ceedling*|*ctest*|*pytest*|*make\ test*)
    filtered="${cmd% && *} 2>&1 | tail -n 100"
    printf '{"hookSpecificOutput":{"hookEventName":"PreToolUse","updatedInput":{"command":%s}}}' \
      "$(printf '%s' "$filtered" | jq -Rs .)"
    ;;
  *)
    printf '%s' "$input"
    ;;
esac
chmod +x ~/.claude/hooks/filter-test-output.sh

Verifique com /hooks e com claude --debug-file ./claude-debug.txt (procure por modified tool input keys).

Outras fontes de consumo silencioso: /loop, goals com check-in em idle, scheduled tasks, mensagens cross-session e sugestões de próximo prompt. Todos enviam o contexto cheio mesmo quando você não está digitando. Desligue o que não presta serviço.

// .claude/settings.json

    "Stop": [
      {
        "hooks": [
          {
            "command": "ceedling test:all >/dev/null 2>~/.claude/stop-error.txt || { cat ~/.claude/stop-error.txt >&2; exit 2; }"

      }
    ]
  }
}

Exit 2 devolve a saída para o Claude e impede o término. O que vai para stderr vira o motivo. Se ele bloquear 8 vezes seguidas sem tool call, o harness cede na próxima (limite configurável com CLAUDE_CODE_STOP_HOOK_BLOCK_CAP).

4. Menos risco

4.1 Camadas de proteção

  1. Permission mode — auto (classifier, padrão no CLI/VS Code desde v2.1.283) bloqueia curl | bash, deploy de produção, migrações, force push sobre trabalho de outros, envio de dados sensíveis a endpoint externo e ações aparentemente induzidas por conteúdo lido. Ainda é julgamento de modelo: pode errar.
  2. Deny rules + hooks — onde mora o seu "nunca". Determinístico.
  3. Sandbox do SO — limita filesystem e rede de comandos de shell e processos filhos.

bypassPermissions só em container descartável. manual é seguro, mas depois da décima confirmação você começa a aprovar sem ler.

4.2 O que o sandbox cobre — e o que fica FORA

Dentro: Bash, PowerShell, Monitor e processos que eles iniciam.

Fora (importantíssimo):

  • tools Read, Edit, Write, WebFetch, WebSearch — seguem *permission rules*, não o sandbox;
  • hooks, MCP servers locais, LSP, status line, plugins monitors, mods;
  • comandos que você digita no prompt !;
  • excludedCommands;
  • o retry dangerouslyDisableSandbox.

Consequência prática: denyRead pega cat .env, não pega um script Python que abre .env. Um deny de WebFetch para gitlab.com não barra curl https://gitlab.com a menos que o sandbox esteja ligado.

4.3 Strict sandbox no Linux (STM32 toolchain)

sudo apt-get install -y bubblewrap socat
claude --settings '{"sandbox":{"enabled":true,"allowUnsandboxedCommands":false,"failIfUnavailable":true}}'
  • allowUnsandboxedCommands: false — ignora o escape hatch dangerouslyDisableSandbox.
  • failIfUnavailable: true — se bwrap/socat faltarem, o Claude Code não inicia. É o comportamento correto quando sandbox é requisito.
  • Dentro: /sandbox → abas *Mode*, *Overrides*, *Config*, *Dependencies*.

Padrões de escrita: working dir + temp + --add-dir/permissions.additionalDirectories. Rede: sem rota direta, proxy com allowlist que começa vazia.

4.4 Credenciais: deny e mask

{
  "sandbox": {
    "credentials": {
      "files": [
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITLAB_TOKEN", "mode": "mask", "injectHosts": ["gitlab.com"] },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    },
    "network": {
      "allowedDomains": ["gitlab.com"],
      "tlsTerminate": true
    }
  }
}
  • deny → arquivo bloqueado, variável removida antes do comando.
  • mask → comando vê um *sentinel*; o proxy troca pelo valor real apenas em injectHosts permitidos. Exige network.tlsTerminate: true.
  • mask com injeção real só é aceito em user settings, managed settings ou --settings — não em .claude/settings.json do repo.
  • Não existe deny list padrão: se você não declarar, nada é protegido.

4.5 Hooks que não deixam passar

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "command": "./scripts/block-generated.sh",
            "onFailure": "block"
          }
        ]
      }
    ]
  }
}

onFailure: "block" impede a ação se o scanner cair ou der timeout. Sem isso, um hook de segredos quebrado deixa o commit passar sem varredura — o que é pior do que não ter hook.

Use command, http ou mcp_tool para imposição. Hooks do tipo prompt ou agent consultam outro modelo, logo não são determinísticos.

Arquivo Quem Efeito

.claude/settings.local.json você, neste repo não versionado
.claude/settings.json time, versionado deny vale na hora; allow depende do trust dialog
managed settings admin/MDM ninguém sobrescreve — referência rápida neste workshop

Mantenha o conjunto imposto pequeno. Todo hook e deny rule vai disparar errado alguma vez e alguém tem que manter. 40 regras quase sempre são 37 preferências disfarçadas.

1. Subagents: paralelismo e olhar independente

Subagents não servem só para "proteger o contexto" — eles hoje são usados principalmente para paralelismo e independência de julgamento.

projeto/
└── .claude/agents/
    ├── reviewer.md        # Read, Grep, Glob — não edita
    └── hil-analyst.md     # lê logs de falha da bancada
---
name: hil-analyst
description: Analisa logs de testes HIL e falhas de hardware; nunca grava firmware.
tools: Read, Grep, Glob
model: haiku
---

Leia artifacts/hil/*.log. Agrupe falhas por causa raiz provável.
Termine com no máximo 10 linhas e liste o REQ afetado.

Quando usar

Situação Use
Busca ampla no repo Explore (nativo)
Revisão sem viés subagent que não viu a conversa / /code-review
Log longo que não deve poluir a conversa subagent em background, pedir resumo curto
Tarefa simples e repetitiva model: haiku
Precisa de contexto que só a conversa tem fork da conversa atual

Custo

Cada subagent faz suas próprias requisições e conta contra o mesmo limite. Um agente novo precisa coletar contexto que você já tinha — às vezes é mais lento que fazer no lugar. Por isso:

  • peça resumo curto de volta;
  • use Haiku para trabalho simples;
  • verifique a fatia de consumo em /usage;
  • desligue agentes/teammates quando terminarem.

2. Hooks: pontos do loop

Evento Uso típico em firmware
SessionStart checar ferramentas (arm-none-eabi-gcc, st-flash, glab) e avisar se faltar
PreToolUse bloquear edição em Drivers/**; reescrever comando de teste para tail -100
PostToolUse formatar C com clang-format após Edit/Write
Stop exigir ceedling test:all verde antes de encerrar
SessionEnd salvar resumo de contexto em .docs/ (nunca commitado)

Exemplo: formatador determinístico

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "command": "clang-format -i \"$FILE\" 2>/dev/null || true" }
        ]
      }
    ]
  }
}

Prefira um script seu a um one-liner frágil. E lembre: se a formatação é preferência, fica no prompt; se é gate, vira hook com onFailure: "block".

Cuidados

  • Hook do tipo prompt/agent não é determinístico — usa modelo para decidir.
  • workspace trust decide quando hooks de um repo recém-clonado começam a rodar.
  • .claude/settings.json versionado afeta todo mundo que clonar. Deny rules valem imediatamente; allow rules esperam o trust dialog.

3. MCP vs CLI: a decisão certa para GitLab

MCP é excelente quando você precisa de ferramentas com significado (criar issue com campos, ler MR com threading, consultar docs internas). O custo é que nome/instruções das tools entram no contexto.

CLI é melhor quando o comando é simples e você quer contexto mínimo:

# prefira isto para operações corriqueiras
glab issue list --label REQ-001
glab mr create --fill --title "REQ-001: piscar LED de status"
glab mr view 42

# MCP só onde a riqueza de dados compensa
/mcp

Regras práticas:

  1. Definições de tools MCP são deferidas por padrão — o nome entra, o schema completo entra quando usado.
  2. /mcp mostra os servidores; desligue os que não usa.
  3. /usage mostra o percentual atribuído a cada servidor — dado real para decidir.
  4. Em sandbox, MCP local roda fora dele. Trate servidor MCP como código confiável seu.

Exemplo de .mcp.json mínimo (somente se você decidir que precisa):

{
  "mcpServers": {
    "gitlab": {
      "command": "npx",
      "args": ["-y", "@gitlab/mcp-server"],
      "env": { "GITLAB_PERSONAL_ACCESS_TOKEN": "$GITLAB_TOKEN" }
    }
  }
}

Confira o nome do pacote e as variáveis na documentação atual do GitLab antes de usar. O ponto aqui é o *padrão*, não a flag exata.

Módulo 05 — TDD e testes unitários em C para STM32

1. Por que testar no host

O firmware roda no STM32, mas a lógica não precisa. Separe:

app/                     ← regras de negócio: testável no host
  blink.c                   (sem HAL direta)
platform/stm32f1/        ← HAL, registradores, st-link
test/                    ← Unity + CMock, roda no PC

O serviço recebe uma interface, não a HAL:

// app/gpio_port.h
typedef struct {
    void (*write)(uint16_t pin, int value);
    int  (*read)(uint16_t pin);
} GpioPort;

void blink_init(const GpioPort *port);
void blink_toggle(void);
int  blink_is_error(void);

No host, você injeta um mock. Na placa, você injeta a HAL. A regra não muda.

#include "blink.h"

static const GpioPort *g_port;
static int g_error;
static int g_level;

void blink_init(const GpioPort *port) {
    g_port = port;
    g_error = 0;
    g_level = 0;
    g_port->write(LED_PIN, g_level);
}

void blink_enter_error(void) {
    g_error = 1;
}

void blink_toggle(void) {
    g_level = g_error ? 1 : (g_level ? 0 : 1);
    g_port->write(LED_PIN, g_level);
}

int blink_is_error(void) { return g_error; }

4. Casos de borda que o modelo esquece

Guarde isto em .claude/skills/embedded-unit-tests/references/edge-cases.md:

Domínio Caso Por que importa
Timer 32-bit @1 kHz rollover em 49,7 dias comparação com valor absoluto quebra
Buffer circular head == tail com cheio vs vazio off-by-one clássico
ISR reentrância / variável volatile corrupção silenciosa
DMA underrun/overrun dado travado ou repetido
ADC 0, UINT32_MAX, canal desconectado leitura fantasy
I2C NACK, clock stretching, busy travamento do barramento
Reset watchdog, brownout estado inicial inválido

O artigo da Beningo sobre skills cita explicitamente rollover de timer de 32 bits, wraparound de buffer circular e reentrância de ISR. O artigo da BTC mostra o outro lado: se a IA não consegue gerar o teste a partir do requisito, o requisito está ambíguo.

5. Mock de HAL sem perder a sanidade

Se você precisar testar algo que chama HAL_GPIO_WritePin, configure o CMock para gerar o mock do header da HAL — mas nunca inclua a HAL real no teste:

:cmock:
  :mock_prefix: mock_
  :plugins:
    - ignore
    - callback
    - expect_any_args
  :treat_externs: :include

Regra para o agente (vai no CLAUDE.md):

- Em test/, nunca inclua stm32f1xx_hal.h. Use mock_*.h.
- Se um teste precisar de hardware real, ele NÃO é unitário: mova para tests/hil/.

  2. todo cálculo com timer/contador;
  3. toda conversão de unidade;

  4. Tente finalizar uma mensagem com a suíte vermelha (quebre uma asserção). O Stop hook deve devolver o erro e não deixar terminar.

8. Checklist

  • □ Teste roda no host, sem placa.
  • □ Regra de negócio não inclui header de HAL.
  • □ Escrevi o teste antes da implementação.
  • □ edge-cases.md tem pelo menos 6 entradas.
  • □ Stop hook barra turno com teste vermelho.
  • □ Cobertura focada em lógica, não em código gerado.

Módulo 06 — CI/CD no GitLab: do commit ao binário com evidência

Tempo: 40 min · Entrega: pipeline build → unit → flash → hil → release no capstone/.

1. O desenho correto para firmware

Separe runners que compilam de runners que tocam hardware. É a decisão de arquitetura mais importante do CI embarcado.

MR aberta
   │
   ├─ build        (runner docker, cross-compiler)  → artefato .elf/.hex/.bin + mapa
   ├─ unit         (runner docker, Ceedling)        → junit + cobertura
   ├─ static       (runner docker, shellcheck/cppcheck)
   │
   └─ manual/tag
      ├─ flash     (runner com ST-Link, tag " stm32-bench")
      └─ hil       (mesmo runner, lock de bancada)   → log + screenshot + junit
          │
          └─ tag v* → release (changelog de MRs + evidência anexada)

Por que separar: um job I2C na bancada não pode rodar em paralelo com outro I2C na mesma placa. A série do stupid-projects mostra exatamente isso com uma test farm de Nanopis rodando gitlab-runner.

2. .gitlab-ci.yml funcional

stages: [build, unit, static, flash, hil, release]

  FIRMWARE: "build/firmware.bin"
  FLASH_ADDR: "0x8000000"

      junit: reports/hil/results.xml

Pontos a notar:

  • flock resolve o lock de hardware no mesmo host. Se a bancada é compartilhada entre hosts, use o Device Cloud do GitLab ou um serviço de alocação.
  • when: manual evita que todo MR gaste a placa. Jobs HIL disparam em MRs marcadas ou em tags.
  • dependencies limita o que é baixado de estágios anteriores.
  • artifacts:reports:junit faz o GitLab mostrar falhas na interface do MR.
  • || true só onde a falha é informativa — nunca no gate principal.

4. Revisão e triagem com Claude no GitLab CI

A documentação oficial coloca GitHub Actions ou GitLab CI/CD como superfícies de automação. O padrão é o mesmo:

  image: registry.gitlab.com/grupo/claude-code:latest

Próximo: Módulo 07 — HIL e bancada.

Módulo 07 — HIL: fechando o loop entre o agente e o hardware

Tempo: 35 min · Entrega: teste HIL com lock, log e evidência no MR.

1. O problema estrutural

"Compila, passa no unit test, grava o firmware... e falha."

O artigo *AI in hardware-in-the-loop testing: the loop embedded never closed* resume bem: o agente não vê o sinal, o rail de 3,3 V, a prioridade de IRQ sob carga ou o NACK do I2C. Enquanto o loop parar no gcc, ele está adivinhando.

HIL é o mecanismo que transforma suposição em observação.

2. As quatro camadas do harness

O Embedded AI Harness do Andreas Spiess (vídeo Nov/2026, ESP32) organiza o loop em quatro camadas. O alvo muda, o desenho não:

HOST    → compila, roda unit tests, gera o binário, decide o próximo passo
TARGET  → STM32 com ST-Link; grava e inicializa
BENCH   → Raspberry Pi / Nanopi: fontes, cargas, analisador lógico, relays, UART
FIELD   → telemetria do equipamento já instalado (opcional, valioso)

Com essa separação, o agente consegue receber evidência estruturada de cada camada em vez de um log gigante.

Camada adicional recomendada: fault injection — cortar o rail, injetar NACK, resetar por watchdog. É o que separa "teste bonito" de "teste que sobrevive à produção".

3. Test farm com GitLab Runner

Baseado na série DevOps for Embedded (stupid-projects), com STM32F103:

Nanopi (gitlab-runner, tag stm32-bench)
 ├── /dev/ttyUSB0        → UART do STM32
 ├── ST-Link USB         → st-flash
 ├── GPIO expander I2C   → mede o pino sob teste
 └── lock file           → /tmp/stm32-bench.lock

Regras de ouro:

  1. Um job por placa por vez. I2C e flash não são reentrantes.
  2. Sempre resetar para estado conhecido antes do teste.
  3. Sempre desligar a carga no after_script.
  4. Gravar o log mesmo na falha (artifacts: when: always).
  5. Não compartilhar runner de build com runner de bancada.

4. Exemplo de teste HIL em pytest

# tests/hil/test_gpio.py
import subprocess, time, serial, pytest

UART = "/dev/ttyUSB0"
BIN = "build/firmware.bin"
ADDR = "0x8000000"

@pytest.fixture(scope="session", autouse=True)
def flash_and_boot():
    subprocess.run(
        ["st-flash", "--reset", "write", BIN, ADDR], check=True
    )
    time.sleep(0.5)
    yield
    # after: desliga periféricos / volta ao estado seguro

def test_led_blinks_at_500ms():
    with serial.Serial(UART, 115200, timeout=3) as ser:
        edges = []
        start = time.monotonic()
        while time.monotonic() - start < 3 and len(edges) < 4:
            line = ser.readline().decode(errors="replace").strip()
            if line.startswith("LED:"):
                edges.append((line, time.monotonic()))
        assert len(edges) >= 4, f"arestas insuficientes: {edges}"
        deltas = [t1 - t0 for (_, t0), (_, t1) in zip(edges, edges[1:])]
        assert all(0.45 <= d <= 0.55 for d in deltas), deltas

5. O que o agente deve receber de volta

Não despeje o log cru. Use um script de resumo (o mesmo padrão do hook de filtro):

E no prompt do agente:

Isso é o hil-analyst do Módulo 04. O custo fica baixo (Haiku + resumo) e o sinal alto.

6. Fault injection que vale a pena

Falha injetada O que você valida
Cortar 3,3 V por 10 ms brownout, estado inicial, reset limpo
NACK no I2C retry com backoff, timeout, liberação do barramento
Watchdog estourado recuperação e logging da causa
DMA underrun dado travado/repetido detectado
UART saturado perda de mensagem sem corromper o estado

Cada injetado deve ter um REQ-### correspondente. Se não tem, você está testando curiosidade, não requisito.

Módulo 08 — Rastreabilidade: do requisito ao artefato

Tempo: 30 min · Entrega: cadeia REQ → Issue → commit → MR → pipeline → release validada por script.

1. Rastreabilidade é cadeia, não documento

Um documento de requisitos bonito que ninguém atualiza é pior que nada. O que importa é conseguir responder, em 30 segundos:

"Por que essa linha de blink.c existe, quem aprovou e qual evidência prova que ela funciona?"

A cadeia:

SPEC.md (REQ-001)
   ↓
Issue #42  (label REQ-001)
   ↓
commit feat(REQ-001): piscar LED de status #42
   ↓
MR !17  (Closes #42, checklist de evidência)
   ↓
pipeline: unit ✓  HIL ✓  junit anexado
   ↓
release v1.4.2  (changelog gerado dos MRs)

2. GitLab Issues como âncora

O GitLab Requirements Management está em transição para *work items* (epic #5171). Para um dev individual, o desenho pragmático é:

  • spec versionada no repo (SPEC.md ou docs/specs/REQ-001.md);
  • Issue com o mesmo ID e label;
  • MR que fecha a Issue (Closes #42);
  • evidência de CI como artefato do pipeline.
glab issue create \
  --title "REQ-001: LED de status" \
  --label REQ-001,firmware \
  --description "Critérios em SPEC.md. Evidência: job hil:gpio."

glab mr create --fill \
  --title "REQ-001: piscar LED de status" \
  --description "Closes #42\n\n- [ ] unit\n- [ ] HIL\n- [ ] ADR atualizado"

3. Convenção de commit

<tipo>(<REQ>): <resumo imperativo> #<issue>

feat(REQ-001): piscar LED de status #42
fix(REQ-003): retry no I2C após NACK #47
test(REQ-001): cobre rollover do timer #42
docs(REQ-001): registra decisão de OSAL #42

Tipos: feat, fix, test, refactor, docs, chore, ci.

O ID aparece duas vezes (no escopo e no #issue) de propósito: uma para o script validar, outra para o GitLab linkar.

4. Validador determinístico

Não confie no agente para lembrar. Coloque no PreToolUse ou no CI:

#!/usr/bin/env bash
# scripts/check-traceability.sh
set -euo pipefail

msg_file="${1:-.git/COMMIT_EDITMSG}"
msg=$(cat "$msg_file")

if [[ "$msg" =~ ^(feat|fix|test|refactor|docs|chore|ci)\(REQ-[0-9]{3}\) ]]; then
  if [[ "$msg" =~ \#([0-9]+) ]]; then
    echo "OK: requisito e issue presentes"
    exit 0
  fi
fi

echo "ERRO: use tipo(REQ-NNN): descricao #issue" >&2
exit 2

No GitLab CI, valide o *range* do MR:

trace:commits:
  stage: static
  script:
    - |
      for c in $(git log --format=%s "$CI_MERGE_REQUEST_DIFF_BASE_SHA"..HEAD); do
        ./scripts/check-traceability.sh <(printf '%s' "$c") || exit 1
      done
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

E no hook local:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "command": "./scripts/hook-commit-guard.sh", "onFailure": "block" }
        ]
      }
    ]
  }
}

O script só intercepta git commit, chama o validador e deixa todo o resto passar.

5. ADR com seção Compliance

# ADR-007 — Isolar HAL atrás de GpioPort

- Status: aceito
- REQ: REQ-001, REQ-004

## Contexto
A HAL gerada pelo CubeMX muda entre revisões. Testes no host não podem incluí-la.

## Decisão
Toda lógica de app/ recebe uma interface GpioPort injetada.

## Alternativas
1. Chamar HAL diretamente — rejeitado: impossível testar no host.
2. Copiar a HAL para test/ — rejeitado: divergência silenciosa.

## Consequências
+ Testes determinísticos no host.
+ Um adaptador por família de MCU.

## Compliance
- Verificação: `test/test_blink.c` usa mock_gpio_port.h; CI falha se app/ incluir stm32f1xx_hal.h.
- Onde roda: job `unit:ceedling` + grep no stage static.
- Evidência: artifact `build/artifacts/test/*.xml`.

A seção Compliance é o que impede a ADR de virar literatura. Ela responde: como uma máquina prova que essa decisão foi respeitada?

Módulo 09 — Releases e governança leve

Tempo: 25 min · Entrega: tag de release com changelog e evidência anexada.

1. Release é um contrato, não um zip

Para firmware, release precisa responder:

Pergunta Onde está
O que mudou? changelog gerado dos MRs mesclados
Qual versão do firmware está gravada? string de versão no binário + tag vX.Y.Z+k<revisão>
Quais requisitos foram validados? relatório de cobertura + junit do HIL
Quem aprovou? MR com aprovação e compliance check
Como reproduzir? commit SHA + imagem da toolchain + docs/ops/verification.md

2. Versionamento com chave de hardware

O padrão que funciona bem quando o firmware acompanha revisão de placa:

v1.4.2+k7
│ │ │ └─ revisão de hardware/placa (k7)
│ │ └─── patch
│ └───── minor
└─────── major

A chave k7 evita um clássico: gravar v1.4.2 de placa revisão 6 em placa revisão 7. No CLAUDE.md:

- A tag de release segue vMAJOR.MINOR.PATCH+kREV.
- Nunca grave firmware com `k` diferente da revisão do hardware de destino.

E no C:

#define FW_VERSION "v1.4.2+k7"

O job de build extrai a tag e falha se a constante divergir:

tag="${CI_COMMIT_TAG:-dev}"
grep -q "$tag" app/version.h || { echo "versão divergente" >&2; exit 2; }

3. Changelog a partir de MRs

release:tag:
  stage: release
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/'
  script:
    - glab release create "$CI_COMMIT_TAG" build/firmware.bin \
        --notes "$(./scripts/changelog.sh)"
#!/usr/bin/env bash
# scripts/changelog.sh
echo "## Mudanças"
git log --pretty=format:'- %s' "$(git describe --tags --abbrev=0 HEAD^)"..HEAD \
  | grep -E '^- (feat|fix)'
echo
echo "## Evidência"
echo "- Pipeline: $CI_PIPELINE_URL"
echo "- HIL: artifact reports/hil/results.xml"
echo "- Cobertura: artifact build/artifacts/gcov/"

4. Runbook de verificação

docs/ops/verification.md deve ser curto e executável:

# Verificação de release v1.4.2+k7

1. Baixe o artefato `fw-<sha>` do pipeline <link>.
2. Confira a string de versão na UART: `FW v1.4.2+k7`.
3. Rode `./scripts/verify-image.sh firmware.bin` (checksum + header).
4. Reexecutar HIL: ver `reports/hil/results.xml`.
5. Se falhar: `/rewind` no commit anterior e abra Issue com label `regression`.

Nota importante sobre o caso real que estudamos antes: num repositório sem histórico Git local, commits/issues são conhecidos apenas por documentação e referências #NN. Não faça isso. Release sem histórico verificável é só um binário órfão.

5. Revisão final antes de taguear

Quatro verificações, em ordem de custo:

  1. Prompt/agente: /verify — Claude builda, roda e olha o resultado.
  2. Revisor independente: /code-review numa MR, subagent que não viu a conversa.
  3. Gates determinísticos: Stop hook local + CI (unit, static, HIL, traceabilidade).
  4. Checklist humana: 5 itens no máximo. Checklist longa ninguém lê.
- [ ] Versão no binário bate com a tag
- [ ] HIL verde no commit exato da tag
- [ ] ADRs de REQs afetados atualizados
- [ ] Changelog gerado de MRs
- [ ] Artefato e junit anexados ao release

6. Governança corporativa (referência rápida)

Não é alvo deste workshop, mas saiba que existe:

  • Compliance frameworks no GitLab: exigem aprovação/checks específicos em MRs.
  • Managed settings: única fonte de regra que o dev não consegue sobrescrever; vem de console/MDM.
  • ZDR / HIPAA / CMEK: restrições de recursos gerenciados — alguns recursos de review na nuvem ficam indisponíveis.

Para dev individual, o equivalente saudável é: .claude/settings.json versionado + CI obrigatória + proteção de branch. Não precisa de MDM para ter disciplina.

Módulo 10 — Capstone: montando o sistema completo

Tempo: 60 min · Entrega: o diretório capstone/ copiado para um projeto GitLab STM32 real.

1. Objetivo

Reunir tudo em um esqueleto reutilizável. O capstone não é um firmware completo — é a configuração que faz o firmware completo ser desenvolvido com segurança, rastreabilidade e custo consciente.

capstone/
├── CLAUDE.md                         ← restrições curtas e universais
├── SPEC.md                           ← REQ-001 com critérios testáveis
├── .gitlab-ci.yml                    ← build → unit → static → flash → hil → release
├── .claude/

4. Auditoria final (o que um revisor deve perguntar)

  1. Existe alguma regra escrita só em texto que deveria ser hook? Se sim, mova.
  2. CLAUDE.md tem mais de 200 linhas? Migre procedimentos para skills.
  3. O agente consegue editar código gerado? Se consegue, o deny rule falhou.
  4. Um turno termina com teste vermelho? Se termina, o Stop hook falhou.
  5. O HIL roda em todo push? Se roda, você está queimando bancada à toa.
  6. Dois jobs I2C podem rodar juntos? Se podem, você vai corromper a bancada.
  7. Dá para rastrear o binário até o REQ? Se não dá, a release é órfã.
  8. /usage mostra >30% em um MCP que você usa uma vez por semana? Desligue.

Apêndice — GitLab vs GitHub Actions (e referência rápida)

Este workshop prioriza GitLab porque o projeto de destino é GitLab + STM32. O material oficial trata os dois como superfícies de primeira classe, mas os detalhes operacionais diferem.

1. Comparação curta

Assunto GitLab GitHub Actions
Pipeline .gitlab-ci.yml .github/workflows/*.yml
Unidade de trabalho job dentro de stage job dentro de workflow
Revisão de código MR, glab mr PR, gh pr
Runner com hardware tags: [stm32-bench] + self-hosted runner runs-on: [self-hosted, stm32-bench]
Artefatos artifacts: com reports: junit: actions/upload-artifact + dorny/test-reporter
Lock de bancada flock no runner ou Device Cloud flock no runner ou serviço externo
Revisão por IA na nuvem integração documentada via GitLab CI/CD Claude Ship (Team/Enterprise) e GitHub Action
Comentários inline MR review via glab/API REVIEW.md só no serviço gerenciado do GitHub
Triagem de Issues automação via GitLab CI + glab GitHub Action + gh
Agendamento pipeline schedule ou /schedule schedule: no workflow

Regra de ouro: a lógica TDD/HIL/rastreabilidade é independente do forge. O que muda é a casca (comandos glab vs gh, sintaxe do YAML, onde o junit aparece).

2. Equivalências de comando

# listar pipeline
glab ci status                       |  gh run list

# ver log
glab ci trace <job-id>               |  gh run view --log

# criar MR / PR
glab mr create --fill                |  gh pr create --fill

# comentar
glab mr note 17 -m "HIL verde"       |  gh pr comment 17 -b "HIL verde"

# baixar artefato
glab ci artifacts <job-id>           |  gh run download <run-id>

3. Sobre /code-review local

  • Funciona em qualquer plano, dentro do terminal, revisando o diff local.
  • Em GitLab, para comentar diretamente na MR você depende de glab autenticado: /code-review --comment !123.
  • REVIEW.md é específico do serviço gerenciado do GitHub; não é um formato universal de relatório.
  • Claude Ship (review gerenciado) é recurso Team/Enterprise, ligado por Owner, cobrado à parte e indisponível com ZDR/HIPAA/CMEK. Não faça plano dependendo dele sem confirmar.
